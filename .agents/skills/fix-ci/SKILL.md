# Fix CI (mslsrc/ome on Buildkite)

Every check on a mslsrc/ome pull request is a Buildkite step generated by
`.buildkite/generate_pipeline.py`. Each step posts a GitHub commit status whose
context equals its step key, so `gh pr checks` and the Buildkite job list name
the same things. There are no GitHub Actions workflows for this repository;
never propose one. Buildkite org `msl`, pipeline `ome`, REST base
`https://api.buildkite.com/v2/organizations/msl/pipelines/ome`.

Work from evidence, in this order: build, failed job, cleaned log, first real
error, local reproduction, fix, local gates, push, watch. Load a reference only
when the current step needs it:

| Reference | Load when |
|---|---|
| `references/pipeline-steps.md` | you need a step's command, retry policy, gating, or when it is emitted |
| `references/failure-signatures.md` | you have a log and need its class (infra, drift, code, known flake) and the action |
| `references/local-reproduction.md` | you need to reproduce a lane locally (envtest, KIND, scheduler, drift, rollout lock) |
| `references/fix-hygiene.md` | you are about to branch, commit, push, retry, or quarantine a KIND spec |
| `references/buildkite-api.md` | raw endpoints, token scopes, JSON and log quirks, artifacts, agent-pod evidence |

## Prerequisites

- A Buildkite user API token in `$BUILDKITE_API_TOKEN` or in `~/.buildkite/token`
  (mode 600) with `read_builds`, `read_build_logs`, `read_artifacts`, and
  `write_builds` for retries. The helper refuses to run without one. Never write
  a token into the repository, a skill file, or a chat message.
- `gh auth status` succeeds for `mslsrc/ome`.
- Scratch (cleaned logs, downloads) lives under
  `~/.cache/ome-agent.noindex/scratch/fix-ci/` (override `OME_FIXCI_SCRATCH`),
  never under the repository.

The helper is standard-library Python and keeps no state:

```sh
S=.agents/skills/fix-ci/scripts/ci_build.py
python3 $S find --pr <n>                 # builds for the PR head commit (also --commit, --branch)
python3 $S status <build>                # every job: key, state, exit, attempts, infra-or-code guess
python3 $S classify <build>              # failed jobs' logs matched against known signatures
python3 $S log <build> <job|key> --grep 'FAIL|Error|FATAL'   # cleaned log, saved to scratch
python3 $S artifacts <build> <job|key> [--download DIR]
python3 $S verdicts <build> [--job <key>] [--all] [--json]   # eval lanes' per-case verdicts from their verdict files
python3 $S retry <build> <job|key>       # PUT .../jobs/<id>/retry, newest attempt only
python3 $S wait <build>                  # poll until the build is terminal
```

## The pipeline at a glance

Runs on every PR and on `main` (step key = GitHub context):

| Family | Step keys | Runs |
|---|---|---|
| Hygiene | `git-author-email`, `internal-tokens` | author-email check; `hack/check_internal_tokens.py --tree` |
| Go | `lint`, `vet`, `test`, `scheduler-test` | `make ci-lint`, `make vet`, `.buildkite/run_tests.sh`, `.buildkite/run_scheduler_tests.sh` |
| Suites | `integration-test`, `perf-test` (soft-fail), `rollout-behavior-lock` | `make integration-test`, `make test-perf`, `make rollout-behavior-lock MACHINE=instance` |
| Charts, console | `helm-lint`, `muse-rust-checks` | `make helm-lint`, `make -C muse ci-rust` |
| Drift | `fmt-drift`, `tidy-drift`, `manifests-drift`, `generate-drift`, `dep-crds-drift`, `oep-status-drift` | `make <target>` then `git diff --exit-code` |
| KIND on GKE | group `integration-test-kind-gke` (children `kind-gke-<slug>`), `package-kind-test-image` | precompiled Ginkgo suite, one three-node KIND cluster per child |
| KIND, advisory | group `integration-test-kind-mc-gke` (`kind-gke-mc-placement`, `kind-gke-mc-quota`), `kind-gke-quarantine` | soft-fail |
| Images, charts | `build-<image>`, `mirror-<image>`, `chart-<chart>` | build validates Dockerfiles on PRs; push and mirror only on `main` |

`main` only: `upload-eval-lanes` (uploads the eval groups and the marker as
further pipeline documents), groups `omenative-e2e-kind-gke-<i>-of-<n>`
(children `omenative-e2e-<feature>-<topology>`), `integration-test-kind-upgrade`
(`kind-gke-upgrade-identity`), `package-kind-eval-image`, `chart-ome-release`
(depends on every other step and group). Kill switches read at pipeline upload: `GKE_KIND_ENABLED`,
`GKE_EVAL_ENABLED`, `GKE_UPGRADE_ENABLED` (default on). A KIND group posts one
GitHub context for the whole group; the failing child is only visible as a
Buildkite job with `step_key` `kind-gke-<slug>`.

## Step 1: locate the build

Prefer PR number, then head SHA, then commit statuses, then the Buildkite build.

```sh
gh pr view <n> --repo mslsrc/ome --json number,headRefOid,headRefName,url,isDraft
gh pr checks <n> --repo mslsrc/ome                       # one line per step key
gh api repos/mslsrc/ome/commits/<sha>/status \
  --jq '.statuses[] | select(.state!="success") | "\(.context) \(.state) \(.target_url)"'
```

The `buildkite/ome` context's `target_url` ends in the build number. Equivalent
in one call: `python3 $S find --pr <n>` (or `--commit <sha>`, `--branch <name>`
when there is no PR). Confirm the build's `commit` is the PR head; an older
build for a superseded commit is not evidence about the current one.

## Step 2: triage each failed job

```sh
python3 $S status <build>        # failed jobs first, with attempts and retried-into ids
python3 $S classify <build>      # signature match per failed job
```

Classify before touching code:

| Signal | Class | Action |
|---|---|---|
| `exit_status` 125, log says `failed to connect to the docker API` or `FATAL: no reachable Docker daemon` | infra: dind daemon | one retry (`retry`); auto-retried already on most steps |
| `signal_reason` `agent_stop`, exit -1, log ends abruptly | infra: agent lost | one retry |
| `cluster create failed in BeforeSuite ... exiting 125` | infra: KIND node boot starved | auto-retried; retry once if the limit was spent |
| `git diff --exit-code` fails on a `*-drift` step | drift | run the named `make` target locally, commit the output |
| `--- FAIL:` / Ginkgo `[FAIL]` with a spec or test name | code | reproduce locally (Step 3); never retry a red spec |
| `soft_failed: true` (`perf-test`, `kind-gke-mc-*`, `kind-gke-quarantine`) | advisory | note it; it does not block merge |
| whole build has one failed upload job and no steps | generator | run the generator locally (Step 3) |

Known flaky signatures that are not the PR's fault: perf
`TestScalability/FunnelBeatsPoll`; `kind-gke-mc-quota` (`Multi-cluster Kueue
quota`) timing out; eval case `p317` under `omenative-e2e-kind-gke` on `main`.
Say so explicitly instead of chasing them; a second identical failure on a
different agent is not a flake.

For the log itself use `log <build> <key> --grep ...` and then read around the
first match (`--context 20`). Buildkite groups a lane's stages under `--- name ---`
headers; the failing stage is the last header before the error. Log format and
raw endpoints are in `references/buildkite-api.md`.

## Step 3: fix

Reproduce first, with the repository's `make` targets rather than raw `go`
(they wire in `KUBEBUILDER_ASSETS`, xet, and pinned tools). The short map; the
full one is `references/local-reproduction.md`:

| Failed step | Reproduce |
|---|---|
| `lint`, `vet` | `make ci-lint` (`make lint-fix` to auto-fix), `make vet` |
| `test` | read the failing `--- stage ---`; unit: `go test ./pkg/<pkg>/... -run <Test> -v` with `KUBEBUILDER_ASSETS="$(bin/setup-envtest use "$(cat .envtest-k8s-version)" -p path)"`; coverage below 48%: `make coverage` |
| `test` (generator stage) | `python3 -m unittest discover -s .buildkite -p 'test_*.py'`; `unclassified KIND specs: <file>` means add the stem to `KIND_SPEC_GROUPS` |
| `integration-test` | `make integration-test`; focused: `go test ./tests/integration/singlecluster/<suite>/... -v` with `KUBEBUILDER_ASSETS` set |
| `scheduler-test` | `cd scheduler && go build ./... && CGO_ENABLED=1 go test -race ./... -count=1` (separate module; `KUBEBUILDER_ASSETS` set) |
| `rollout-behavior-lock` | `make rollout-behavior-lock MACHINE=instance` (`make rolloutspec-check` for the tables alone) |
| `internal-tokens` | `python3 hack/check_internal_tokens.py --tree`; replace the identifier with a neutral one |
| `git-author-email` | set a `@users.noreply.github.com` author and rewrite the offending commits |
| `*-drift` | `make fmt` / `make tidy` / `make manifests` / `make generate` / `make dep-crds` / `make oep-status`, commit |
| `kind-gke-<slug>` | `GINKGO_FOCUS='<It text>' make test-kind` under a throwaway `KUBECONFIG` (see hygiene below) |
| `helm-lint`, `muse-rust-checks` | `make helm-lint`, `make -C muse ci-rust` |
| generator failure | `python3 .buildkite/generate_pipeline.py >/dev/null` and the unittest line above |

Kubeconfig hygiene is a hard rule for any KIND reproduction:
`export KUBECONFIG="$(mktemp -t ome-kind-XXXXXX.kubeconfig)"` before
`make test-kind`, and `rm -f "$KUBECONFIG"` after. Never run
`kubectl config use-context`, and never let `kind` touch the ambient kubeconfig.

Apply directly when the fix is mechanical: formatting or generated-file drift,
a lint finding, a stale import, a test asserting on a renamed field, an
unclassified KIND spec, an internal identifier in a fixture. Present the change
and ask before: logic changes in a controller or the rollout engine, touching
`pkg/apis/ome/v1beta1/` (needs `make manifests && make generate`), altering a
Helm template or chart values, adding a new hardcoded behavioral value
(blocked by repository policy; make it config-driven instead), or quarantining
a KIND spec.

## Step 4: verify, commit, push

Before every push, the repository's gates:

```sh
make fmt && make vet && make ci-lint && make test-no-xet
```

Plus the targeted gate for what you touched: `python3 -m unittest discover -s
.buildkite -p 'test_*.py'` for `.buildkite/`, `python3
hack/check_internal_tokens.py --tree` for any text, `make rolloutspec-check
MACHINE=instance` for rollout tables, `make helm-lint` for charts, `make
manifests && make generate` for API types, `make tidy` for `go.mod`.

Commit as a new commit (no amend) with a GitHub noreply author email; the one
exception is fixing `git-author-email` itself, which requires rewriting the
rejected commits. Branch names follow `<type>/<desc>` or `<username>/<desc>`;
PR titles carry `[Bugfix]`, `[CI/Tests]`, `[Core]`, `[API]`, `[Helm]`,
`[Docs]`, `[Misc]`, or `[OEP]` and stay under 52 characters. Fixing an existing
PR's CI means committing to that PR's branch, not opening a second PR. Before a
new fix for a failure on `main`, check for an open PR aimed at it:

```sh
gh pr list --repo mslsrc/ome --state open --search "<error keyword>"
```

Code comments state the invariant, never the incident, the PR number, or the
build number. Fixtures stay leak-free (neutral hostnames, no internal cluster,
tracker, or people names); the `internal-tokens` step enforces the mechanical
part. Details in `references/fix-hygiene.md`.

## Step 5: watch and iterate

A push creates a new build for the new head SHA. Find it, wait, and re-triage:

```sh
python3 $S find --commit "$(git rev-parse HEAD)"
python3 $S wait <build> --interval 60 --max-minutes 90
python3 $S status <build>
```

Cadence: lint, vet, and drift finish in minutes; `test` and `integration-test`
in tens of minutes; the KIND groups in 30 to 60 minutes. Keep iterating while
each round produces a different error class. Stop, and hand off with the
evidence, when the build is green, when the same error recurs with no change in
class, when a soft-fail lane is the only red, when an infra signature repeats
after one retry (escalate CI infrastructure, do not retry again), or when the
remaining failure is a product defect outside the PR's scope (open an issue).

## Report

End with: build link and head SHA; per failed step the key, class, root cause,
and the decisive log line; what was changed and the commit hash; which steps
were retried and their outcome; whether CI is expected green, and anything left
open (known flake, advisory lane, out-of-scope defect).
