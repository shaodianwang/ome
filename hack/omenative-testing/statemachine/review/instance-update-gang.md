# update-gang — arrows and exceptions

## ARROWS (every outgoing transition of the two states)
| id | from → to | on | guard (as written) | verdict | change / question |
|---|---|---|---|---|---|
| T-gangtarget-ready | Update/GangSurgeTarget → Ready | pod.deleted[source] | paired source on SurgeDrain with pods gone, marker still matches the claim for the pinned revision | KEEP | `promoteGangSurgeTarget` fences on both lifecycle identities and the active-target claim, and it is reached only after every replacement pod is PodReady and past minReadySeconds — the source is never released early. |
| T-gangtarget-cleanup-failed | Update/GangSurgeTarget → Update/GangSurgeTargetCleanup | timer.operationDeadline | the paired source escalated to Failed on this surge before the replacement was promoted | CHANGE | The trigger is the *source's* escalation, not this row's `operation.deadline` (events.yaml defines that event as this operation's own deadline elapsing); re-key it to a paired-source-Failed trigger, and add the `pod.waiting` / `timer.stuckPodGrace` fast paths that reach source-Failed the same way and today have no arrow into Cleanup. |
| T-gangtarget-cleanup-superseded | Update/GangSurgeTarget → Update/GangSurgeTargetCleanup | spec.revision | the source's pinned surge revision is superseded while the replacement gang is incomplete or not runtime-ready | KEEP | Matches `update_gang.go:157-166` exactly, including the empty `failedTargetRev` that suppresses the RetryBlock. |
| T-gangtarget-deadline | Update/GangSurgeTarget → Failed | timer.operationDeadline | the marker's own deadline elapsed with phase Creating and no pod admission-gated; a gang step is never disposable | CHANGE | Two arrows leave the same (state, event) with different destinations and no stated precedence; the guard must say this one lands first (same pass, `escalateFromEvidence`) and that T-gangtarget-cleanup-failed re-claims the already-Failed marker on a later pass because the claim predicates ignore phase. |
| T-gangtarget-stuck-failed | Update/GangSurgeTarget → Failed | pod.waiting | a replacement pod held a terminal waiting reason past the stuck-pod grace, the set is not fully serving, gang steps are never disposable | KEEP | `disposableAttempt` returns false for `GangSurgeTarget`, so the plain Failed-preserving-Operation stamp is correct; see the exception on the missing relocation directive. |
| T-gangtarget-stuckgrace | Update/GangSurgeTarget → Failed | timer.stuckPodGrace | the grace elapsed on a replacement pod holding a terminal waiting reason, the set is not fully serving | KEEP | Same edge as T-gangtarget-stuck-failed reached by the clock rather than the pod event; both windows are modeled. |
| T-gangtarget-teardown | Update/GangSurgeTarget → Delete/Drain | spec.teardown | the owner carries a deletionTimestamp so every observed index is a scale-down extra | KEEP | Teardown short-circuits before the update pass; the marker has no special claim to defend once the owner is going away. |
| T-gangtarget-teardown-deadline | Update/GangSurgeTarget → Empty | timer.teardownDeadline | owner Terminating, configured deadline passed, teardown finalizer still held | KEEP | Leaving the replacement pods and their PodGroup to background GC is the documented teardown-deadline contract, identical to every other state. |
| T-gangcleanup-done | Update/GangSurgeTargetCleanup → Empty | pod.deleted[target] | every pod of the retired replacement is gone and its instance resources are finalized | KEEP | `finalizeAndResetAbandonedGangSurge` commits marker-removal + source-reset + RetryBlock in one `ApplyInstanceMutationsWithRetryBlock`, so marker absence can never be read back as an interrupted stamp. |
| T-gangcleanup-deadline | Update/GangSurgeTargetCleanup → Failed | timer.operationDeadline | the marker's own deadline elapsed with phase Creating and no pod admission-gated | CHANGE | Diagnostic-only: the retirement keeps waiting after the stamp, so the only bounded thing in Cleanup is a label. The deadline must *act* — force-delete the retired pods (the policy `ops/force_delete.go` already implements for scale-down) — or the state has a wait with no deadline at all, which the rubric forbids. |
| T-gangcleanup-stuck-failed | Update/GangSurgeTargetCleanup → Failed | pod.waiting | a retired replacement pod held a terminal waiting reason past the stuck-pod grace, the set is not fully serving | CHANGE | The state's own windowless `pod.waiting` cell says `ignore` for every window, so the arrow and the cell contradict each other; keep the arrow (it is reachable before the delete lands, exactly as the `timer.stuckPodGrace` cell admits) and split the cell. |
| T-gangcleanup-teardown | Update/GangSurgeTargetCleanup → Delete/Drain | spec.teardown | the owner carries a deletionTimestamp so every observed index is a scale-down extra | KEEP | The delete wave is a strictly stronger reaper than the retirement (it has force-delete); superseding is the right precedence. |
| T-gangcleanup-stuckgrace | Update/GangSurgeTargetCleanup → Failed | timer.stuckPodGrace | a retired pod still holds a terminal waiting reason and is not yet marked for deletion | KEEP | Correctly narrowed to the pre-delete window — once the delete lands the classifier skips the pod. |
| T-gangcleanup-teardown-deadline | Update/GangSurgeTargetCleanup → Empty | timer.teardownDeadline | owner Terminating, configured deadline passed, teardown finalizer still held | KEEP | Consistent with every other state's teardown-deadline edge. |

## EXCEPTIONS (cells that contradict their event's meaning, an arrow, or the rubric; include every DECIDE and every # GAP cell)

## ROOT CAUSES
| root cause (file:function) | exceptions it explains | one-line fix shape |
|---|---|---|
| `ops/update_gang.go:gangSurgeUpdate` — the replacement-gang loop treats the live pod list as a name-keyed presence check (no `DeletionTimestamp`/phase filter, no surplus pruning) and never revokes serving on survivors | pod.deleted[target], pod.evicted, pod.containersNotReady[target], pod.terminating[target], pod.phaseTerminal, spec.gangWidth[shrink] | one `effectiveGangMembers` helper that filters terminating/terminal pods and prunes surplus, plus a gang-wide `MarkPodNotServing` whenever the set is incomplete |
| `ops/update_gang.go:gangSurgeUpdate` drain block (lines 300-328) — clears the serving gate and deletes in the same pass, with no `drain.IsPodDrained` and no settle step | endpoint.rotationOut[source]; the absent `Update/GangSurgeDrainSettle` state | reuse `update_surge.go`'s drain-check + settle sequence on the gang path |
| `ops/update_gang.go:abandonFailedGangSurge` / `finalizeAndResetAbandonedGangSurge` — an unbounded delete-and-wait with no force-delete, a diagnostic-only deadline, a `Creating` phase, and the source pinned in `Update/Surge` until it finishes | Cleanup timer.forceDelete, pod.stuckTerminating, timer.operationDeadline, pod.waiting, the Cleanup phase, source-repair suspension | give the retirement a real terminator (force-delete policy + deadline that acts) and a truthful `Deleting` phase |
| `workload/escalation.go:escalateFromEvidence` + `disposableAttempt` — for a non-disposable gang attempt the only action is a phase stamp: no condition, no relocation directive, no unwedging, and no effect on the claim predicates | pod.waiting[7 reasons], T-gangtarget-deadline, T-gangcleanup-deadline, api.invalid | record a relocation/exclusion directive and a named condition on the non-disposable path, not just `Phase=Failed` |
| Nothing reads PodGroup status or `PodScheduled`; `inferencereplica/watches.go:podGroupPredicate` drops status-only updates, and only `inferencereplica/reconciler.go:609` checks the PodGroup sentinels | gang.podGroup[Unschedulable/ScheduleTimeout/PhaseFailed], [OwnershipConflict], [Terminating], pod.unschedulable[target] | watch + read PodGroup status into a marker condition, and check the sentinels on the `workload.Reconcile` error too |
| `ops/update_surge.go:surgeUpdate` — `strategyLeftSurge` and the single-pod recycle sit below the `inst.TotalPods() > 1` gang branch | spec.strategy; the recycle alternative under pod.waiting | move the abandon predicate above the branch, or widen `update_gang.go:157` to include the strategy unwind |
| `coordination/ratio.go:unavailableInFlight` — the surge-step exclusion list omits `UpdateStepGangSurgeTargetCleanup` | the Cleanup phase/aggregate exception | add the Cleanup step to the exclusion switch |
| Authoring hygiene in `cells-update-gang.yaml` / `transitions.yaml` — windowless cells where an arrow exists, cells naming transitions the arrow set lacks, and one arrow modeled under another row's event | Cleanup pod.waiting, Cleanup timer.operationDeadline, spec.rollbackTarget, spec.replicasDown (unreferenced reap), GangSurgeTarget timer.operationDeadline·before, Cleanup timer.minReady reason | one `before` cell per arrow, one arrow per real edge, and reasons that state the invariant rather than the happy path |
