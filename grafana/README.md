# OME Grafana dashboards

Three dashboards for OME, generated by [`gen_dashboards.py`](gen_dashboards.py)
into [`dashboards/`](dashboards/).

| Dashboard | UID | Answers |
|---|---|---|
| OME · Control plane | `ome-control-plane` | Is OME itself reconciling, and how fast? |
| OME · Router | `ome-router` | Which engine backends is the router using, and what latency does it add? |
| OME · Scheduler | `ome-scheduler` | Is work getting placed, and where is placement slow? |

Together they follow one request through OME: the **Control plane** decides what
should exist, the **Scheduler** places the pods, and the **Router** dispatches
traffic to them. When a deployment misbehaves, that is also the order to read them
in — a stalled reconcile, an unplaceable gang, and an ejected backend look
identical from the outside and are three different problems.

Engine-side serving metrics (SGLang / vLLM latency, tokens, KV cache) are
deliberately **not** covered here; the Router dashboard stops at the router's own
view of the request.

## Grafana vs the MUSE console

They answer different questions, and neither replaces the other:

- **MUSE** (the console) is **current state** from informer caches — what exists
  right now and whether it is healthy. Its System panel (OEP-0021.2) reports
  desired-vs-ready for the control plane, including a component that is scaled to
  zero or **not deployed at all** — states no metric can express, because absence
  of a series is not the same as a component being absent.
- **Grafana** is **change over time** — reconcile rates, latency percentiles,
  saturation trends, and the shape of an incident before and after.

Use MUSE to see *what is broken*; use these dashboards to see *how it got there*.

## Importing

Each file is a self-contained dashboard JSON with a required `${datasource}`
variable, so nothing is pinned to one Grafana instance:

- **UI:** Dashboards → New → Import → upload the JSON → pick your Prometheus.
- **Provisioning / GitOps:** point a dashboard provider at `dashboards/`, or wrap
  each file in a ConfigMap labelled for your Grafana sidecar.

## Where the data comes from

### Label conventions differ by backend — read this before debugging "No data"

OME's **bundled** Prometheus stamps `namespace`, `pod`, `inferenceservice`, and
`component`. A **fleet-wide** store (a central Grafana Cloud / query-gateway
backend aggregating many clusters) may not: observed there, OME control-plane
series carry `cluster`, `cluster_id`, `pod`, `k8s_pod_name`, `controller`,
`result` — and **no `namespace` label at all**.

The control-plane and scheduler dashboards therefore scope by **`cluster` + pod
name** (`pod=~"ome-controller-manager.*"`, `pod=~"ome-scheduler.*"`) rather than by
namespace. That is both portable and safer: a fleet store can contain *other*
systems' `scheduler_*` metrics (a managed-Kubernetes provider's own
kube-schedulers, which carry no `pod` label), and the pod-name guard keeps them out
of the OME scheduler dashboard.

Beware the silent case: in PromQL `label=~""` matches series where the label is
**absent**, so a namespace filter against a store with no `namespace` label appears
to "work" while actually filtering nothing.

Selector labels come from OME's own scrape relabeling
(`charts/ome-resources/templates/prometheus/configmap.yaml`), which stamps
`namespace`, `pod`, `inferenceservice`, and `component` onto InferenceService pod
series, plus a `cluster` external label.

### Dependencies, and what to adjust

| Dashboard | Needs | If it's empty |
|---|---|---|
| Control plane | OME control-plane pods scraped (the `prometheus.io/scrape` annotation the chart sets) and standard controller-runtime metrics | Confirm the pods are scraped. Scoping is by `cluster` + pod name, not namespace (see above). |
| Router | OME router pods exporting the `router_*` family | Confirm router pods are scraped. |
| Scheduler | `ome-scheduler` (OEP-0022) scraped. It is built on the upstream Kubernetes scheduler framework, so the standard `scheduler_*` metrics apply | Confirm the scheduler pods are annotated for scraping. The OME-specific gang/domain metrics are **not** wired — see the note panel at the bottom of that dashboard. |

## Regenerating

Edit `gen_dashboards.py` — not the JSON — then:

```sh
python3 grafana/gen_dashboards.py
```

The dashboards are generated so they share one panel vocabulary — units,
threshold steps, legend behavior — across all three.
