# OME Grafana dashboards

Five dashboards for OME, generated by [`gen_dashboards.py`](gen_dashboards.py)
into [`dashboards/`](dashboards/).

| Dashboard | UID | Answers |
|---|---|---|
| OME · SLO | `ome-slo` | Are we meeting our deployment targets, and is OME up? |
| OME · Control plane | `ome-control-plane` | Is OME itself reconciling, and how fast? |
| OME · Router | `ome-router` | Which engine backends is the router using, and what latency does it add? |
| OME · Scheduler | `ome-scheduler` | Is work getting placed, and where is placement slow? |
| OME · Multi-cluster control plane | `ome-mc-control-plane` | Is the management cluster healthy, and is the placer reconciling? |

The middle three follow one request through OME: the **Control plane** decides what
should exist, the **Scheduler** places the pods, and the **Router** dispatches
traffic to them. When a deployment misbehaves, that is also the order to read them
in — a stalled reconcile, an unplaceable gang, and an ejected backend look
identical from the outside and are three different problems.

**SLO** sits above all three. It is the on-call landing page: two indicators —
did the deployment succeed, and how long did it take — plus the uptime of the
components that have to be running for either number to mean anything. It is a
claim about history rather than about right now, which is why it has different
backend requirements from the others (see below).

**Multi-cluster control plane** stands apart from the other four: it targets a
*management* cluster running the placer and the quota plane, not a workload
cluster. Its panels are all generic — controller-runtime, kube-state-metrics, and
the apiserver's object counter — because neither the placement stack nor the
quota stack registers a custom metric. It can show that the control plane is
running; it cannot show that it is placing correctly. The dashboard's last panel
says so, and lists the fix for each gap.

Engine-side serving metrics (SGLang / vLLM latency, tokens, KV cache) are
deliberately **not** covered here; the Router dashboard stops at the router's own
view of the request.

## Grafana vs the MUSE console

They answer different questions, and neither replaces the other:

- **MUSE** (the console) is **current state** from informer caches — what exists
  right now and whether it is healthy. Its System panel (OEP-0021.2) reports
  desired-vs-ready for the control plane, including a component that is scaled to
  zero or **not deployed at all** — states no metric can express, because absence
  of a series is not the same as a component being absent.
- **Grafana** is **change over time** — reconcile rates, latency percentiles,
  saturation trends, and the shape of an incident before and after.

Use MUSE to see *what is broken*; use these dashboards to see *how it got there*.

## Importing

Each file is a self-contained dashboard JSON with a required `${datasource}`
variable, so nothing is pinned to one Grafana instance:

- **UI:** Dashboards → New → Import → upload the JSON → pick your Prometheus.
- **Provisioning / GitOps:** point a dashboard provider at `dashboards/`, or wrap
  each file in a ConfigMap labelled for your Grafana sidecar.

## Where the data comes from

### Label conventions differ by backend — read this before debugging "No data"

OME's **bundled** Prometheus stamps `namespace`, `pod`, `inferenceservice`, and
`component`. A **fleet-wide** store (a central Grafana Cloud / query-gateway
backend aggregating many clusters) stamps a different and larger set, and the
exact set depends on *which collector reached the pod* — see the next section,
which is the thing to read before writing a query against a fleet store.

Do not assume a fleet store drops `namespace`: measured against the central store,
control-plane series carry `cluster`, `cluster_id`, `k8s_cluster_name`, `pod`,
`k8s_pod_name`, `namespace`, `k8s_namespace_name`, `container`, `service`,
`endpoint`, `controller`, and `result`. An earlier revision of this file claimed
there was no `namespace` label there; that was drawn from
`ome_isvc_status_update_total`, which has no `namespace` label of its own to begin
with, and it does not generalise.

The control-plane and scheduler dashboards therefore scope by **`cluster` + pod
name** (`pod=~"ome-controller-manager.*"`, `pod=~"ome-scheduler.*"`) rather than by
namespace. That is both portable and safer: a fleet store can contain *other*
systems' `scheduler_*` metrics (a managed-Kubernetes provider's own
kube-schedulers, which carry no `pod` label), and the pod-name guard keeps them out
of the OME scheduler dashboard.

Beware the silent case: in PromQL `label=~""` matches series where the label is
**absent**, so a namespace filter against a store with no `namespace` label appears
to "work" while actually filtering nothing.

Selector labels come from OME's own scrape relabeling
(`charts/ome-resources/templates/prometheus/configmap.yaml`), which stamps
`namespace`, `pod`, `inferenceservice`, and `component` onto InferenceService pod
series, plus a `cluster` external label.

### One producer, several collectors — pin one, or every number is a multiple

A component can be collected more than once, by independent pipelines that stamp
different labels. Each collection is a legitimate, separate series, so PromQL sums
them and the panel is silently 2-3x too high. This is the most common way to get a
confidently wrong number out of a fleet store, and it does not look like an error.

Three cases seen against the central store:

| Producer | Collected by | Discriminator |
|---|---|---|
| `ome-controller-manager` | the chart's ServiceMonitor **and** an annotation-driven `kubernetes-pods` job | `endpoint="metrics"` — only the ServiceMonitor path sets `endpoint`, and only it carries `namespace` and `pod` |
| kube-state-metrics | two replicas, both exporting the same state | `max by (...)`, never `sum` |
| kube-apiserver | one series per apiserver instance | `max by (...)`, never `sum` |

The concrete failure: `sum(leader_election_master_status{...})` over an unpinned
manager reads **2** on a healthy three-replica deployment and looks exactly like
split brain. The multi-cluster dashboard pins all three cases; copy its selectors
(`MC_MGR`, `MC_KSM`, `MC_API` in `gen_dashboards.py`) rather than writing new ones.

Check for this before trusting any new panel:

```promql
count by (job, endpoint, container) (<your_metric>{cluster="<cluster>"})
```

More than one row means more than one collector, and the query needs a
discriminator.

### Dependencies, and what to adjust

| Dashboard | Needs | If it's empty |
|---|---|---|
| SLO | A long-retention store scraping **both** the OME control plane and kube-state-metrics | See "The SLO dashboard needs a different backend" below. |
| Control plane | OME control-plane pods scraped (the `prometheus.io/scrape` annotation the chart sets) and standard controller-runtime metrics | Confirm the pods are scraped. Scoping is by `cluster` + pod name, not namespace (see above). |
| Router | OME router pods exporting the `router_*` family | Confirm router pods are scraped. |
| Scheduler | `ome-scheduler` (OEP-0022) scraped. It is built on the upstream Kubernetes scheduler framework, so the standard `scheduler_*` metrics apply | Confirm the scheduler pods are annotated for scraping. The OME-specific gang/domain metrics are **not** wired — see the note panel at the bottom of that dashboard. |
| Multi-cluster control plane | A management cluster running the placer, with the manager scraped, kube-state-metrics running, and the apiserver scraped | The `cluster` picker is `label_values(controller_runtime_reconcile_total{controller="placement"}, cluster)`, so an empty picker means no scraped cluster is running the placer at all. Per-panel gaps are listed in the dashboard's own coverage panel. |

### The SLO dashboard needs a different backend

The other three work against any Prometheus that scrapes OME. The SLO dashboard
does not, for two reasons:

- **Retention.** OME's bundled Prometheus is configured with `retention: 30m`
  and exists to feed KEDA, not to answer questions about yesterday. An SLO is a
  statement about a window — a day, 28 days — so it needs a store that keeps one.
- **kube-state-metrics.** `SLI 1` is built on
  `ome_inferenceservice_transition_status`, which is *not* exported by OME's own
  binaries. It comes from kube-state-metrics running with
  [`config/monitoring/kube-state-metrics-config.yaml`](../config/monitoring/kube-state-metrics-config.yaml)
  applied and `--custom-resource-state-config-file` pointed at it. The bundled
  Prometheus does not scrape KSM at all.

`SLI 2` (`ome_isvc_time_to_ready_seconds`) *is* exported by the
controller-manager, so it only needs the control plane scraped.

Note that these two indicators disagree by construction, and the disagreement is
informative: SLI 1 is a gauge ratio over the ISVCs that exist right now, while
SLI 2 is a histogram over deployments that completed. A fleet where every ISVC is
`UpToDate` but nothing has deployed in a week reads as 100% on the first and
"No data" on the second.

#### What the deployment SLIs do not cover

- **Cold vs. warm model loads are not separable.** Serving pods are pinned to
  model-resident nodes by a hard `nodeSelector`, so the pod is not created until
  the weights are already local. The download happens before there is anything
  to measure, and no series distinguishes the two cases.
- **`deploy_kind` is inferred, not recorded.** `create` means the ISVC reported
  `Ready=Unknown` beforehand and `update` means it reported `Ready=False`. A
  first deploy that briefly flaps to `False` before coming up is counted as an
  update.

## Regenerating

Edit `gen_dashboards.py` — not the JSON — then:

```sh
python3 grafana/gen_dashboards.py
```

The dashboards are generated so they share one panel vocabulary — units,
threshold steps, legend behavior — across all five.

Nothing enforces this: there is no CI drift check, so a hand-edited JSON survives
until someone next runs the generator and silently reverts it. Regenerate and
commit the JSON in the same change as the generator edit.

### Verify a panel before you ship it

A panel querying a metric that does not exist renders "No data", or worse renders
a threshold colour — a stat panel with a red base step reads as a live incident
forever. Both failure modes have shipped here before. Query each new expression
against the real store first:

```sh
# Instant query through Grafana's datasource proxy. <ds-uid> is the Prometheus
# datasource UID; substitute a real value for every dashboard variable.
curl -sS -H "Authorization: Bearer $GRAFANA_TOKEN" \
  --data-urlencode 'query=<expr>' \
  "$GRAFANA_URL/api/datasources/proxy/uid/<ds-uid>/api/v1/query"
```

An empty `data.result` means the panel will be blank. Fix the query, or drop the
panel and record the gap in the dashboard's coverage panel — an honest note beats
a permanently empty graph.
