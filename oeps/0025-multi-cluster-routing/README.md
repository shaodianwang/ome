# OEP-0025: Multi-Cluster Routing — capacity-aware traffic maps

**Tl;dr:** Placement decides *where* an InferenceService's replicas run; quota
decides *how much* each cluster may run; but the global router today weights
clusters only by their live ready-replica count — a purely reactive signal with
no notion of intended capacity and no stable contract for a gateway to consume.
This OEP adds **`TrafficMap`**: a per-ISVC, control-plane-generated,
**capacity-planned, health-gated** routing table that a gateway-neutral publisher
programs onto a real data plane. It is the routing *projection* of placement +
quota, in the same way OEP-0024's distributor projects budgets onto Kueue.
Opt-in via Helm; SMG is one optional backend, not a hard dependency.

> Status: provisional / alpha. Contains visible `TBD`s where a decision is still
> open (see Open Questions). Dates are absolute so staleness is visible.

## Summary

OME can already place an InferenceService (ISVC) across workload clusters
(OEP-0018: `Single`/`All`/`Split`) and budget accelerator capacity per cluster
(OEP-0024: `AcceleratorQuota`). The runtime facts of a placement already land in
`InferenceService.status.placement.candidates[]` — each home carries its
`endpoint` URL, `admittedReplicas`, and `readyReplicas`. The existing Gateway API
publisher (`pkg/controller/v1beta1/placement/endpoint/gatewayapi.go`) already
turns those `readyReplicas` into HTTPRoute backend weights.

That is enough for *reactive* routing and nothing more. This OEP closes three
gaps:

1. **No capacity intent in the weights.** Weight = current ready replicas. A home
   that is *supposed* to carry 70% of the fleet (because placement apportioned it
   and quota admitted it) carries whatever fraction happens to be `Ready` this
   second. Weights swing with autoscaling and cold starts, not with the plan.
2. **No stable, consolidated contract.** A gateway must watch *every* ISVC and
   reassemble the routing table itself from `status.placement`. There is no single
   object per routed service that says "here is the traffic split, and here is why."
3. **Cutoff is implicit.** Traffic to a failed home drops only as its
   `readyReplicas` collapses to zero, at whatever pace readiness converges.

`TrafficMap` is one namespaced object per ISVC, owned by the ISVC, written by a
new control-plane routing controller, and consumed by a pluggable publisher.
Weight = **capacity allocation** (Split apportionment ∩ quota-admitted count)
**gated by health** (a home with zero ready replicas gets zero weight). The
publisher stays gateway-neutral: the current Gateway API HTTPRoute path retargets
to read `TrafficMap`, and SMG (OME's serving router) is one optional backend
enabled from Helm.

## Motivation

### The failure modes we are fixing

- **Weight drift under autoscaling (the reactive-weight anti-pattern).** With
  ready-replica weighting, a home scaling from 2→8 replicas silently quadruples
  its share of global traffic mid-flight, even though the *plan* (placement +
  quota) never said it should carry more. Conversely a home mid-cold-start is
  under-weighted exactly when you provisioned it to take load. The router chases
  runtime state instead of enforcing intent.
- **Gateway coupling.** Any gateway that wants to route multi-cluster traffic must
  today watch all ISVCs and re-derive the split. That couples the data plane to
  the ISVC schema and to control-plane internals, and makes per-namespace RBAC
  for "who may see the routing table" awkward — the routing table is smeared
  across every ISVC's status.
- **Slow / unclear cutoff.** When a whole home is lost — the OEP-0018 case of a
  cluster disconnecting, or the practical case of a large TPU failure domain going
  down — traffic drains only as `readyReplicas` decays. There is no single place
  that says "this home is out; its weight is 0 now."

### Why now

We have the two inputs a real traffic map needs. Placement gives the **set of
homes and their endpoints**; `Split` gives the **per-home replica apportionment**;
`AcceleratorQuota` gives the **admitted capacity denominator**. Before OEP-0018
and OEP-0024 there was nothing to compute a capacity-aware weight *from*. Now
there is — the missing piece is the projection and the contract.

### Goals

1. **Introduce a `TrafficMap` CRD** (`ome.io/v1beta1`), one per ISVC, namespaced,
   owner-referenced to the ISVC, generated by a control-plane routing controller
   from `status.placement` + `AcceleratorQuota` allocation. *Rationale:* a stable,
   single-object contract per routed service that a gateway can watch without
   knowing the ISVC schema.
2. **Compute weights as capacity-planned, health-gated.** Weight tracks the
   intended per-home allocation and drops to 0 only when a home has no ready
   replicas. *Rationale:* enforce the plan, but never black-hole traffic onto a
   dead home.
3. **Keep the publisher gateway-neutral.** Define the consumption contract
   independent of any one data plane; retarget the existing Gateway API HTTPRoute
   publisher to `TrafficMap`; support SMG as an optional Helm-deployed backend.
   *Rationale:* upstreamable contract, pluggable data plane (matches the existing
   `endpoint` package design, which already anticipates "backends added later").
4. **Fast, explicit cutoff.** A home losing all ready replicas — including a whole
   failure domain going down — reflects as weight 0 in `TrafficMap` within one
   reconcile, and the publisher reprograms the data plane accordingly.
5. **Opt-in.** Multi-cluster routing (and any gateway it deploys) is enabled from
   Helm; disabled, behavior is exactly today's.

### Non-Goals

- **Redefining placement or quota.** `TrafficMap` *reads* their outputs; it does
  not decide where replicas go or how much capacity a home has. Those stay in
  OEP-0018 / OEP-0024.
- **Intra-cluster routing.** How traffic is balanced *inside* a home (across pods,
  across a TPU failure domain) is the local Service / in-cluster gateway's job.
  `TrafficMap` weights *homes*, not pods. (The TPU-failure-domain cutoff concern is
  addressed one level down; see *Interplay* and the standing discussion in
  placement.)
- **L7 traffic policy.** Header-based routing, retries, timeouts, consistent-hash
  keys, and per-revision canary weights are OEP-0011 (inference-traffic-policy)
  and the rollout OEPs. `TrafficMap` carries only per-home endpoints + weights +
  health. It composes *under* an L7 policy; it does not replace it.
- **Hand-authoring routing.** `TrafficMap` is generated, not written by operators
  (see Alternatives for why the hand-authored variant was rejected).
- **Specifying a gateway data plane.** SMG's image and deployment topology are
  Helm/GitOps concerns and stay out of this (upstreamable) document; SMG's internal
  TrafficMap watcher lives in the SMG repo, not here.

## Proposal

### Terms (defined before use)

- **Home.** A workload cluster currently serving (a share of) an ISVC — a
  `Candidate` in `status.placement.candidates[]` that reached `Placed`/`Admitted`
  and reported an addressable `endpoint`. "Home" = one routing target.
- **Capacity allocation.** The number of replicas a home is *intended* to run for
  this ISVC: in `Split`, the apportioned share (`status.placement.candidates[].admittedReplicas`,
  bounded by `spec.placement.split`), intersected with what the home's
  `AcceleratorQuota` actually admits. In `Single`/`All` there is no fractional
  split, so allocation is uniform (see below). This is the *numerator* of a
  home's weight.
- **Health gate.** A boolean per home: `readyReplicas > 0`. A home that fails the
  gate contributes weight 0 regardless of its allocation — the mechanism that cuts
  traffic to a down home.
- **TrafficMap.** The per-ISVC CRD holding the computed routing table: one entry
  per home with its endpoint, weight, and the capacity/health provenance of that
  weight.
- **Publisher.** The control-plane component that programs a concrete data plane
  from a `TrafficMap` (Gateway API HTTPRoute, SMG, …). Pluggable; one active per
  install.
- **Gateway.** The data plane that actually splits client traffic across home
  endpoints per the programmed weights.

### The one API type: `TrafficMap`

`TrafficMap` is the routing projection, deliberately analogous to how OEP-0024's
distributor projects an `AcceleratorQuota` tree onto native Kueue objects: the
control plane owns and writes it; humans read it but never edit it.

```yaml
apiVersion: ome.io/v1beta1
kind: TrafficMap
metadata:
  name: llama-3-70b            # same name as the ISVC
  namespace: team-a
  ownerReferences:             # owned by the ISVC; GC'd with it
    - apiVersion: ome.io/v1beta1
      kind: InferenceService
      name: llama-3-70b
      controller: true
spec:
  service: llama-3-70b         # the routed logical service (the ISVC)
  mode: Split                  # mirrored from spec.placement.mode
  # entries is the routing table: one per serving home, controller-generated.
  entries:
    - cluster: gke-us-east-1
      endpoint: https://llama-3-70b.team-a.us-east-1.example.com
      weight: 70               # capacity-planned, health-gated (see below)
      healthy: true
      capacity:                # provenance for the weight; why it is what it is
        allocated: 7           # intended replicas on this home
        ready: 7               # live ready replicas (the health signal)
        factor: "1.0"          # per-replica relative capacity c_h (heterogeneous HW)
    - cluster: gke-eu-west-1
      endpoint: https://llama-3-70b.team-a.eu-west-1.example.com
      weight: 30
      healthy: true
      capacity:
        allocated: 3
        ready: 3
        factor: "1.0"
  observedISVCGeneration: 42   # the ISVC generation this table was computed from
status:
  programmed: true             # written by the publisher, not the generator
  gatewayRef:                  # which data plane object realizes this map
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: llama-3-70b
  observedTrafficMapGeneration: 5
  conditions:
    - type: Programmed
      status: "True"
      reason: HTTPRouteReconciled
```

Two controllers, one object, a clean write split (states the ownership so the
reader knows who may write what):

- The **routing controller** (generator) owns `spec`: it recomputes `entries`
  whenever `status.placement` or the home's `AcceleratorQuota` allocation changes.
- The **publisher** owns `status`: it programs the data plane and reports whether
  the map is realized (`Programmed`).

*Anticipated objection — "a machine-written `spec` is unusual; spec is user
intent."* True, and we considered a status-only shape (Alternatives). We keep the
computed table in `spec` because it is a *declarative artifact* the publisher
consumes like any other desired state — the split from generation (control plane)
and realization (publisher) is exactly the ISVC→derived-ISVC split OME already
uses. The object is never hand-edited; a validating webhook may reject writes from
non-controller users to make that explicit.

### How a weight is computed: capacity-planned, health-gated

For each home `h` with allocation `a_h`, per-replica capacity factor `c_h`, and
ready count `r_h`:

```
raw_h    = a_h × c_h      if r_h > 0        # planned serving capacity, while alive
raw_h    = 0              if r_h == 0       # health gate: no ready replicas → no traffic
weight_h = normalize(raw_h)                 # Gateway API weights are relative ints
```

- In **`Split`**, `a_h` is the apportioned/admitted replica count already in
  `status.placement.candidates[].admittedReplicas`. Traffic follows the *plan*
  (7:3 above), not the live `readyReplicas` — so a home scaling 7→9 under a load
  spike does **not** steal a larger share of global traffic; its local autoscaler
  absorbs the spike, the global split holds.
- In **`All`**, every home is a full replica of the service; allocation is uniform
  (`a_h = 1` for each healthy home) → equal split, minus any home that fails the
  gate. In **`Single`**, exactly one home is weighted (the winner); the map still
  exists so cutover on a failed winner is expressible.
- **Heterogeneous hardware — the capacity factor `c_h`.** Replicas are not fungible
  across accelerators: 100 replicas on GB300 and 100 on TPU is not a 50/50 split if a
  GB300 replica serves 2× the tokens/sec. `c_h` is the *per-replica relative serving
  capacity* on home `h` (baseline `1.0`, higher = faster), so `raw_h = a_h × c_h` —
  the GB300/TPU example yields `200:100 → 2:1`. Resolution is config-driven with
  precedence: (1) an explicit per-accelerator/per-home factor on the ISVC
  (`spec.placement`) — the accurate source, since the ratio is workload-specific
  (model × runtime × precision), not a hardware constant; (2) an opt-in
  `AcceleratorClass` default; (3) `1.0` if unset. **`c_h` is never auto-derived from
  `AcceleratorClass` TFLOPS** — raw FLOPS is not a reliable throughput proxy across
  GPU vs TPU. With homogeneous hardware every `c_h = 1.0` and the math reduces to
  today's replica-count weighting. This changes *weighting only*, not placement:
  `Split` still apportions replicas; `c_h` converts replicas → capacity for the
  traffic split.
- The **health gate is binary in v1**: `r_h == 0 → weight 0`, otherwise the full
  planned weight. *Failure mode this avoids:* a proportional gate
  (`weight ∝ ready/allocated`) would swing weights on every transient readiness
  dip and reintroduce exactly the reactive drift we are removing. *Cost we accept:*
  a home at 1/7 ready still receives its full 70% share and may briefly overload.
  Whether v2 graduates to a *bounded* proportional gate is an Open Question.

### End-to-end flow

1. **Placement + quota run (existing).** The fan-out race and `Split`
   apportionment populate `status.placement.candidates[]` with each home's
   `endpoint`, `admittedReplicas`, `readyReplicas`; `AcceleratorQuota` governs what
   each home admitted.
2. **Routing controller generates `TrafficMap` (new).** It watches the ISVC (its
   `status.placement`) and the relevant `AcceleratorQuota` allocation, computes the
   capacity-planned health-gated weights, and writes `TrafficMap.spec`. One
   `TrafficMap` per ISVC, owner-referenced for GC.
3. **Publisher programs the data plane (retargeted).** The Gateway API publisher
   reads `TrafficMap.spec.entries` (instead of re-deriving from `status.placement`)
   and reconciles one HTTPRoute with a backendRef + weight per home; the optional
   SMG publisher programs SMG. It writes `TrafficMap.status.programmed`.
4. **Cutoff.** A home losing all ready replicas flips `healthy:false`/`weight:0` in
   the next controller reconcile; the publisher reprograms; the gateway stops
   sending to that home.

### Why a CRD and not just ISVC status (the objection, answered head-on)

This is the fork the author explicitly weighed. The per-ISVC routing facts *do*
already exist in `status.placement`; the question is whether to consolidate them.

| Dimension | Reuse `status.placement` only | New `TrafficMap` CRD (derived) |
|---|---|---|
| Gateway coupling | Gateway watches **all** ISVCs, re-derives split | Gateway watches **one** object kind per service |
| Capacity-aware weights | No — ready-replicas only | Yes — allocation ∩ quota, health-gated |
| Stable contract / RBAC | Routing smeared across ISVC status | One object, own RBAC, own webhook |
| Extra machinery | None | +1 CRD, +1 controller writing a machine `spec` |
| Where routing "why" lives | Nowhere consolidated | `entries[].capacity` provenance |

**Pick: `TrafficMap`, derived from `status.placement`.** `status.placement` stays
the source of truth for *placement facts*; `TrafficMap` is the *routing
projection* of those facts plus quota — the same layering as OEP-0024 (budgets in
the CRD, enforcement projected onto Kueue). We are not duplicating state; we are
adding the projection that makes capacity-aware weights and a gateway-neutral
contract possible.

## Design Details

### `TrafficMap` schema (v1)

- `spec.service` (string, required): the routed ISVC name (== `metadata.name` in
  v1; a distinct field leaves room for a future many-ISVC-to-one-service map).
- `spec.mode` (enum `Single|All|Split`): mirrored from `spec.placement.mode` so a
  consumer need not read the ISVC.
- `spec.entries[]` (list, `listMapKey: cluster`): one per serving home.
  - `cluster` (string, required): the `WorkloadCluster` name.
  - `endpoint` (URL, required): the home's addressable URL (from
    `status.placement.candidates[].endpoint`).
  - `weight` (int32, ≥0): the normalized, capacity-planned, health-gated weight.
  - `healthy` (bool): the health-gate result (`readyReplicas > 0`).
  - `capacity.allocated` / `capacity.ready` (int32) and `capacity.factor`
    (quantity, per-replica relative capacity `c_h`, default `1.0`): weight
    provenance — `weight ∝ allocated × factor`, health-gated.
- `spec.observedISVCGeneration` (int64): the ISVC generation the table was
  computed from, for staleness detection.
- `status.programmed` (bool), `status.gatewayRef` (typed ref),
  `status.observedTrafficMapGeneration` (int64), `status.conditions[]` (standard).

### Ownership & lifecycle

- **One `TrafficMap` per ISVC**, `metadata.name == isvc.name`, namespaced to the
  ISVC. *Rationale:* mirrors HTTPRoute-per-service; trivial ownership, GC, and
  RBAC; scales linearly with ISVC count (no single hot object).
- **Owner-referenced to the ISVC** (`controller: true`) → deleted by Kubernetes GC
  when the ISVC is deleted. The publisher additionally removes the programmed data
  plane objects on `TrafficMap` deletion via a finalizer, so a route never
  outlives its map.
- **Created only for multi-cluster ISVCs** (those with `spec.placement`), and only
  when routing is enabled (Helm). A `Single`-mode ISVC gets a one-entry map so
  winner-cutover is expressible; a non-placement ISVC gets none.
- **The map exists for the whole life of the ISVC, even with zero entries.** It is
  created as soon as the ISVC is placer-owned and routing is on, and is deleted
  only by GC when the ISVC goes away or by the Helm toggle going off. Emptiness is
  a *state of the map*, never its absence. *Rationale:* absence is unattributable
  — feature off, ISVC not placed, no addressable home, and a wedged controller all
  look identical, so the operator's only recourse is manager logs. Worse, deleting
  on degradation removes the object exactly when it is most wanted: a map that has
  been serving real traffic disappears the moment its last home stops being
  addressable, taking `capacity.allocated`, `capacity.ready` and the per-home
  factors with it — the very fields that say *what* went away. Kubernetes makes the
  same call for the same kind of object: a selector `Service` keeps its
  `EndpointSlice` when no pod is ready, marking addresses `conditions.ready:
  false`, and an empty slice for no pods at all. `TrafficMap` is that object for a
  fleet, so it behaves that way.
- **An empty map must say why it is empty**, or we have traded "absent and
  ambiguous" for "present and ambiguous". The router owns a `Routable` condition on
  `status.conditions` — `True` when at least one entry is addressable, otherwise
  `False` with a machine-readable reason: `NotPlaced`, `NoAddressableHome`, or
  `AllHomesUnready`. *Rationale:* a zero-entry map still cannot distinguish "the
  placer has not chosen homes" from "the homes exist but publish no endpoint"; the
  reason is what makes the object debuggable rather than merely present.
  `status.conditions` is already a `listType=map` keyed on `type`, so the router's
  `Routable` and the publisher's `Programmed` coexist under server-side apply
  without either clobbering the other — but they are two writers on one subresource
  and each must patch only its own condition.

Note what this does *not* change: health is already an entry field, not a gate.
`Healthy: readyReplicas > 0` is per-entry, an admitted-but-unready home is already
emitted, and the weight function already has an explicit all-zero branch ("every
home is zero — equal-weight fallback so traffic is never black-holed"). Degradation
was representable everywhere except when it was total; this closes that gap.

### Publisher contract (pluggable, gateway-neutral)

The `endpoint` package already frames publishing as pluggable ("the Gateway API
HTTPRoute backend is the first; backends added later without touching the
reconciler"). This OEP formalizes that: a `Publisher` reads a `TrafficMap` and
reconciles exactly one data plane realization, reporting `status.programmed`.

- **Gateway API HTTPRoute publisher** (retargeted from today's status-reading
  path): one HTTPRoute, one `backendRef` per home (an ExternalName Service
  aliasing the home endpoint, as today), `weight` per entry. When all weights are
  0 (e.g. every home unhealthy) it must **not** black-hole — it falls back to
  equal weight, matching today's guard in `gatewayapi.go`.
- **SMG backend** (optional): SMG (OME's serving router) consumes `TrafficMap`
  **natively** — a TrafficMap watcher inside SMG populates its worker registry and
  splits across homes by the entry weights. Because we own the SMG codebase this is
  a native reflector (mirroring SMG's existing pod service-discovery), not an
  out-of-process adapter or xDS push. Here SMG is the consumer, so this "publisher"
  is a no-op beyond marking `status.programmed` from SMG's readiness; the *contract*
  is identical — SMG reads `TrafficMap`.

Exactly one publisher is active per install, selected by config (no in-code
default; see below).

### Enabling routing, and the no-magic-values rule

Per the repo's hard constraint (no behavioral value baked into the binary),
routing is entirely config-driven:

- A Helm toggle (e.g. `ome.multicluster.routing.enabled`) gates the routing
  controller and publisher; **default off**, and off means today's behavior.
- The active publisher (`gatewayapi` | `smg`), the gateway/gatewayClass ref, the
  backend port, and any host template come from the operator ConfigMap / Helm
  values — **no in-code fallbacks**. Absent config degrades gracefully (routing
  simply not programmed), it does not inject a default gateway name or host.
- Deploying SMG itself (image, replicas, service) is a Helm concern in the
  internal chart; the upstreamable code only references it through the
  config-supplied publisher selector and refs.

### Where it runs

The routing controller runs in the **control plane** (OEP-0019), alongside the
placement fan-out controller — it needs the aggregated `status.placement` across
homes, which only the control plane sees. The publisher also runs there (it
programs a global gateway object). Neither runs on workload clusters.

### Interplay with adjacent OEPs

- **OEP-0018 placement.** `TrafficMap` is downstream of placement: it consumes
  `status.placement.candidates[]`. It changes nothing about the race, GC, or
  `Split` apportionment. If placement is cluster-granular (it is), so are
  `TrafficMap` entries — one per home, never per pod.
- **OEP-0024 quota.** `AcceleratorQuota` is the capacity denominator: a home's
  `allocated` is bounded by what its ClusterQueue admitted. If quota is disabled,
  allocation falls back to the `Split` apportionment alone (Open Question: is that
  the right denominator when there is no quota?).
- **OEP-0011 traffic policy & rollout OEPs.** These own *L7* behavior and
  *per-revision* (canary/blue-green) weights *within* a home. `TrafficMap` owns
  *cross-home* weights. They compose: the per-revision split is applied at the
  home; the cross-home split is applied at the global gateway. Keeping them
  separate is deliberate — conflating them would put revision rollout state into a
  cross-cluster object.
- **OEP-0023 status URLs.** `TrafficMap.entries[].endpoint` reuses the per-home
  addressable URLs that OEP-0023 standardized; this OEP does not invent a new URL
  scheme.
- **TPU / large failure domains.** `TrafficMap` cuts a *home* fast (health gate →
  weight 0). Cutting a *sub-cluster* failure domain (a TPU pod hosting many
  replicas) is a level below and out of scope here; the fast-cutoff value
  `TrafficMap` adds is for whole-home loss.

## Test Plan

- **Unit (weight math).** Table-driven: `Split` 7:3 with both healthy → 70/30; one
  home `ready:0` → 100/0; all homes `ready:0` → equal-weight fallback (no
  black-hole); `All` mode → uniform minus unhealthy; `Single` → one entry.
- **Controller (envtest).** ISVC `status.placement` transitions → `TrafficMap.spec`
  converges; ISVC deletion → `TrafficMap` GC'd; quota allocation change → weights
  recomputed; `observedISVCGeneration` tracks the source.
- **Publisher (envtest).** `TrafficMap.spec` → one HTTPRoute with per-home weighted
  backendRefs; entry removed → backendRef dropped, stale ExternalName Service
  deleted; `status.programmed` set; finalizer removes route on map deletion.
- **Integration (multi-cluster harness, OEP-0020).** End-to-end: fan-out → admit →
  `TrafficMap` generated → gateway programmed → kill a home → weight→0 within one
  reconcile. The real-Kueue multi-cluster suite gates the capacity-aware path.
- **Leak-free fixtures** (`example.com`, generic cluster names) per the upstreaming
  boundary.

## Graduation Criteria

- **Alpha.** CRD + generator + Gateway API publisher behind the Helm toggle
  (default off). `Split`/`All`/`Single` weight math + binary health gate. Unit +
  envtest coverage.
- **Beta.** SMG publisher; multi-cluster integration suite gating cutoff and
  capacity-aware weights; documented consumption contract; scale test at TBD ISVC
  count.
- **Stable.** Default-on decision made (or explicitly kept opt-in with rationale);
  proportional-gate Open Question resolved; conformance for a second gateway
  backend proving the contract is genuinely neutral.

## Drawbacks

- **A new CRD + controller.** More moving parts and a machine-written `spec` (an
  unusual shape we justify above). If most installs never enable multi-cluster
  routing, this is carrying cost for a subset — mitigated by the default-off toggle.
- **Two objects can disagree transiently.** `TrafficMap` derived from
  `status.placement` can lag placement by a reconcile; `observedISVCGeneration`
  makes the lag observable but does not eliminate it.
- **Binary health gate can overload a barely-ready home** (accepted; see the weight
  section and Open Questions).

## Alternatives

1. **Reuse `status.placement` only (no CRD).** Simplest; already partly built.
   Rejected as the *primary* design because it cannot deliver capacity-aware
   weights or a decoupled contract (see the table above). Note we still *keep*
   `status.placement` — as the source `TrafficMap` derives from, not the consumer
   contract.
2. **Fleet-wide single `TrafficMap`** (one cluster-scoped object, all ISVCs).
   One thing to watch, but a write-contention hotspot, unbounded growth, and
   awkward per-namespace RBAC. Rejected for the per-ISVC shape.
3. **Hand-authored `TrafficMap`** (operator writes weights). Maximum control, but
   throws away the auto-derivation from placement+quota that is the whole point,
   and reintroduces drift between the plan and the routing. Rejected; a future
   *override* field could layer operator intent on top without owning the base.
4. **Reuse Kubernetes `EndpointSlice`.** It already models endpoint + readiness,
   but has no weight/capacity semantics and is cluster-local by design — bending it
   to cross-cluster capacity weights would abuse a well-known type. Rejected.
5. **DNS-weight / external global LB only** (publish weights to DNS). Viable as a
   *publisher* backend later, but coarse (DNS TTL cutoff is slow — bad for the
   fast-cutoff goal). Not the v1 backend.

## Open Questions

0. ~~Should a `TrafficMap` exist when nothing is routable?~~ **Resolved: yes,
   always, with a `Routable=False` reason.** Deleting on degradation made the
   object vanish at the moment of greatest diagnostic value and made a
   never-created map indistinguishable from a broken controller. See
   *Ownership & lifecycle*. Implementation note: the two `reap()` calls in
   `pkg/controller/v1beta1/placement/routing` collapse to one (feature-disabled
   only); the not-placed and no-addressable-home paths become an empty map plus a
   reason.

1. **Proportional vs. binary health gate.** Should v2 scale weight by a *bounded*
   `min(ready/allocated, 1)` to avoid overloading a barely-ready home, or does that
   just reintroduce reactive drift? (Leaning binary for v1, revisit with data.)
2. **Allocation denominator when quota is disabled.** Is the `Split` apportionment
   alone the right `allocated` when there is no `AcceleratorQuota`, or should we
   fall back to ready-replicas (i.e. today's behavior) in that case?
3. ~~How SMG consumes `TrafficMap`.~~ **Resolved: native CRD watch inside SMG.**
   Since we own the SMG codebase, SMG watches `TrafficMap` directly (a reflector
   mirroring its existing pod service-discovery) rather than taking an xDS push from
   an out-of-process adapter. SMG's one real gap is a weighted-split routing policy;
   the feed reuses its existing K8s reflector + worker registry.
4. **Static vs. measured capacity factor `c_h`.** v1 takes `c_h` as operator-supplied
   config (per-ISVC override / `AcceleratorClass` default). Should a later version
   *derive* it from observed per-home tokens/sec (a live measured factor), so
   heterogeneous weights self-tune instead of relying on a hand-set ratio? (Leaning
   static for v1 — measured needs a trusted cross-home throughput metric.)
5. **Per-ISVC vs. per-endpoint granularity for multi-model serving.** If one ISVC
   fronts multiple routable model endpoints, is one `TrafficMap` per ISVC still the
   right unit, or per endpoint? `spec.service` leaves room but v1 assumes 1:1.
6. **Composition with per-revision rollout weights.** Exact ordering when a
   cross-home split (`TrafficMap`) and an in-home canary split are both active —
   confirm the "apply canary at the home, cross-home at the gateway" layering holds
   for every rollout progression.
