# OEP-0020.1: Rollout state-machine specification — exhaustive state × event tables

<!-- toc -->

**Tl;dr:** The OMENative rollout engines are five cooperating state machines, and
nothing in the repo states what each one must do when a given event arrives in a
given state. Behavior is decided one bugfix at a time, and our test corpora —
940 permutation YAMLs, 99 KIND spec files, 58K lines of unit tests — enumerate
*configurations* thoroughly while placing events in only two or three coarse
timing buckets. This OEP writes the machines down as machine-readable tables in
which every applicable (state, event, window) cell has exactly one decided
outcome, and makes the perm corpus, the unit tables, and the KIND specs
*projections* of those tables. The tables are the behavior we want; the tests
merely check the code against them.

## Summary

Five tables, one per machine: the per-Instance lifecycle, the per-Component
revision state, the coordination group, the canary executor, and the rollout
run. Each table lists states, events, transitions with their guards and the
function that decides them, and an exhaustive cell table. A cell is one
(state, event, window) triple and carries one outcome from a closed vocabulary —
`transition`, `ignore`, `defer`, `reject`, `escalate`, `n/a`, or `DECIDE` — plus
a status (`current`, `review`, `decided`), a coverage record, and the bugfix
history that touched it. A well-formedness test fails the build when a cell is
missing or a frozen machine still has a `DECIDE`.

From the tables we derive: cases for the real-cluster permutation runner under
`hack/omenative-testing/perm`, whose fault hook grows from three timing phases to
"when the Instance enters *this* operation step"; table tests at the engines'
pure decision points (`workload.Plan`, `coordination.ComputeTransition`, the
canary step gates, `rolloutrun.Reconcile`); cell-tagged KIND specs for the
windows only a real kubelet can place; and a coverage report that counts
*behaviors* covered rather than YAMLs present.

Scope: the OMENative (IR-managed) path. RawDeployment and MultiNode are unaffected.

## Motivation

### Terminology

- **OMENative** — the deployment mode in which OME manages pods directly rather
  than through a Deployment or LeaderWorkerSet. Every term below is scoped to it.
- **Component** — one serving role of an InferenceService (engine, decoder,
  router). Each OMENative Component is materialized as one **InferenceReplica
  (IR)** object, whose reconciler owns that Component's pods.
- **Instance** — one replica of a Component: a single pod, or a gang of pods
  that must start, stop, and migrate together.
- **Operation** — the durable record an Instance carries while destructive work is
  in flight (`instanceStatuses[].operation` on the IR: type `Create`/`Update`/
  `Restart`/`Migrate`/`Delete`, plus a **step** such as `Surge`, `SurgeDrain`,
  `InPlace`, `Drain`). The step is persisted, which is what makes it observable
  from outside the controller and therefore usable as a test coordinate.
- **Coordination group** — a set of Components rolled together under one policy
  (BlueGreen, RollingUpdate, Sequential, Independent), driven by the
  `coordination` package on the InferenceService side.
- **Canary executor** — the stepped capacity-then-traffic progression for one
  group, driven by the `canary` package.
- **Rollout run** — the pinned plan (`status.rollout.activeRun`) that freezes
  `spec.rollout` for the duration of one rollout, driven by `rolloutrun`.
- **Gate** — a read-only check the IR reconciler makes before starting one
  Instance's update (`coordination.EvaluateUpdateGate`); a denial is recorded as a
  `RolloutHold` with one of seven gate names.
- **Window** — *when* an event lands relative to a transition: `before` (the
  guard is false), `boundary` (the guard just became true but the controller's
  write has not landed), `after` (the next state is persisted).
- **Cell** — one (state, event, window) triple with one decided outcome. "The
  table is exhaustive" means every applicable cell exists, including the ones
  whose outcome is `n/a`.

### The failure modes we are shipping today

**Failure mode 1 — coverage is wide on configuration and blind on timing.** The
permutation corpus under `hack/omenative-testing/perm/isvcs/` holds roughly 940
case YAMLs, 579 of them generated by `generate_cases.py` as the product of
topology (4) × update strategy (4) × failure verb × restart policy × pause mode
(`isvcs/MANIFEST.md`). Its only timing axis is the fault hook's phase set,
`FAULT_PHASES = {"settling", "rotating", "migrating"}` (`perm/run.py:1018`). But
"rotating" is not one state. At the granularity the code persists, an Instance
mid-update is in one of `Surge`, `GangSurgeTarget`, `SurgeDrain`,
`SurgeDrainSettle`, `Drain`, `InPlace`, or `GangSurgeTargetCleanup`
(`pkg/controller/v1beta1/workload/types/types.go:117-132`,
`workload/ops/update_status.go:19-38`), and a pod kill or a spec edit landing in
each is a different behavior. The bugfix history is a list of exactly such cells:
a re-bump during an in-flight surge, scale-up while restarts converge,
`CreateContainerError` on a surge target, a gang member lost below Ready, a
late-joining RatioBalanced member, a partial bump under the Sequential gate,
promotion before the recreated pod was Ready. None of these is a new
*configuration*; each is a known event in a state the corpus could not aim at.

**Failure mode 2 — behavior is decided by accretion.** No artifact says what
should happen when event E hits state S. Each bugfix decides one cell in
isolation, so adjacent cells can be decided inconsistently and nobody can tell.
Two concrete series: the revision-hash exclusions were corrected four times,
each time because one more ambient annotation or label turned out to change the
hash and trigger a roll; and pause semantics were settled in two fixes one day
apart ("pause keeps repair running", then "truthful phase under pause") that
resolve different cells of the same "pause × Instance state" row. Since 2026-06-01, 120 commits touched
`pkg/controller/v1beta1/workload` and 93 touched
`pkg/controller/v1beta1/inferenceservice/reconcilers/omenative`; of the 120 most
recent commits across the two trees, 67 carry the `[Bugfix]` tag. That rate is
the cost of having no table.

**Failure mode 3 — coverage is counted in files, not behaviors.** We have 99 KIND
spec files in `omenative_coordination_kind/` across 27 CI groups, 940 perm cases,
and 42K lines of `workload` unit tests, and none of it can answer the question
"which (state, event) pairs have never been exercised?" OEP-0020 named the
file-count inflation problem (`PIt` placeholders, dead `Skip`s); this is the same
problem one level down. A count of cases is not a coverage number.

**Failure mode 4 — the written specs have drifted from the code.** OEP-0007.1's
controller state table (`README.md:956-1039`) has no `Staged` phase, which the
code has (`pkg/apis/ome/v1beta1/coordination_types.go:290`). The canary phase
enum in the code — `Stable`, `Canarying`, `BlueGreenStandby`, `Pending`,
`Paused`, `Promoting`, `RollingBack`, `RolledBack`, `Failed`
(`traffic_status_types.go:106-136`) — carries two values, `BlueGreenStandby` and `RolledBack`, that
OEP-0015.1's `RolloutPhase` section (`README.md:314`) never lists. So the spec of record is the code, and the code's spec is spread
across roughly 30K lines in two trees. A reviewer cannot check a change against a
spec that exists only as the thing being changed.

### Goals

- **Write every machine down exhaustively.** For each of the five machines, a
  table in which every applicable (state, event, window) cell has exactly one
  outcome, and a build-time check that says so.
- **Make "the behavior we want" an explicit decision.** Cells the code decides
  today are marked `current`; cells the bugfix history touched are marked
  `review`; unclear cells are marked `DECIDE`. A machine is frozen only when an
  owner has turned every `review` and `DECIDE` into `decided`.
- **Derive tests from the table, not the other way round.** Perm cases, unit
  tables, and KIND specs carry the cell id they check, so coverage is computed by
  joining results to cells.
- **Aim the existing real-cluster runner at operation steps**, so a fault or a
  verb can be fired when an Instance enters a named step instead of "somewhere
  during rotation".

### Non-Goals

- **No controller behavior change in this OEP.** Where a `decided` cell differs
  from `current`, the fix is a separate PR that cites the cell. This OEP produces
  the tables, the checks, the runner extension, and the derivation tooling.
- **Not the deterministic simulator.** A seeded in-process simulator that
  explores these tables automatically is the natural next step (Alternatives,
  option 1), and the tables are shaped so it needs no new format. It is a
  separate OEP.
- **Not a formal-methods spec.** No TLA+ / P model. The tables are precise enough
  to generate one later if we want model checking; see Alternatives, option 2.
- **Not RawDeployment, MultiNode, or the multi-cluster placer.** Different
  machines, different OEPs.

## Proposal

### Part 1: five machines, explicit interfaces

The engines are five machines, not one. Each has a small state vocabulary, and
each talks to the others only through persisted objects — IR spec and status,
InferenceService status — or through the update-gate call. That is what lets us
enumerate them separately and compose scenarios by chaining cells instead of
building a product table.

| Machine | Owner package | State vocabulary (from code at `654cde4f`) | Consumes | Emits |
|---|---|---|---|---|
| Instance lifecycle | `workload` (dispatched by the IR reconciler) | 9 phases (`types.go:43-51`) refined by 5 operation types and about 12 steps | pod facts, IR spec, gate verdicts, timers | IR `instanceStatuses[]`, `retryBlocks[]`, `migrations[]` |
| Component revision | IR reconciler + `irprojector` | settled, diverged, staged (partition), held (RetryBlock `Held`), paused, teardown | instance rows, ISVC spec | IR `currentRevision`/`updateRevision`, Ready condition, `rolloutHold` |
| Coordination group | `coordination` | 10 phases (`coordination_types.go:261-304`) × 4 policies; 7 hold gates (`lifecycle_types.go:102-125`) | IR status, pods, ISVC spec/status, clock | `status.rolloutCoordination`, per-Component `traffic[]`, gate deny/allow |
| Canary executor | `canary` | 9 phases (`traffic_status_types.go:106-136`) × step index × 3 pause flavors | IR capacity, analysis results, annotations, clock | `status.canary`, `traffic[]`, IR partition |
| Rollout run | `rolloutrun` | no run; parked (7 reasons, `rollout_run_types.go:228-234`); open; closed (3 outcomes, `:38-44`) | IR targets, `spec.rollout`, RolloutPolicy, annotations | `status.rollout.activeRun`/`lastRun`, plan conditions |

Interfaces are named events. The coordination machine's effect
`gate.deny(Sequential)` is, verbatim, the instance machine's event `gate.deny`.
A cross-machine scenario — "group in `Waiting`, source Instance in `SurgeDrain`,
target pod deleted" — is therefore two cells chained by a shared event id, not a
row in a three-dimensional table.

**Inherited by the InferenceReplica (component) machine.** One row of the
instance grid is one Instance, so the grid is structurally blind to anything
whose subject is the whole replica. Three such items must be in the component
machine's vocabulary from its first commit rather than discovered later. The
invariant `pass.isolates.instances`: one Instance's failing step never stops
the pass for the others, so a single wedged row degrades one Instance and not
the Component. The invariant `status.write.fits`: the per-replica status write
stays under the apiserver's request size limit, so one large service cannot
freeze every cell at once — the instance grid cannot state this because no
single Instance owns the write. And the event `api.requestTooLarge`: an
object-level write rejected for its size, which is not an `api.invalid` and
does not become retriable by waiting.

### Part 2: the table format

One directory of fragments per machine; the block below is the merged,
logical view a loader produces from them. The format is chosen for two
consumers at once: the Python corpus generator, which today emits headers as
text and has no reason to learn Go, and a Go loader that validates ids and
drives the unit tables. (Alternatives, option 5, weighs Go-authored tables.)

```yaml
machine: instance
scope: one Instance of one OMENative Component
states:
  - id: Update/Surge
    phase: Updating
    op: {type: Update, step: Surge}
    applies: {strategies: [SurgeThenDrain], shape: [single, gang]}
    decided_in: pkg/controller/v1beta1/workload/ops/update_surge.go
events:
  - id: pod.ready
    family: pod
    variants: [source, target]
  - id: spec.revision          # a new target ControllerRevision hash
    family: operator
  - id: gate.deny
    family: coordination
    variants: [Plan, Pairing, Ratio, Sequential, Budget, RetryBlock, Held]
  - id: timer.retryAt
    family: timer
transitions:
  - id: surge-to-surgedrain
    from: Update/Surge
    event: pod.ready
    variant: target
    guard: target pod Ready and serving gate on
    to: Update/SurgeDrain
    effects: [source serving gate off]
    decided_in: pkg/controller/v1beta1/workload/ops/update_surge.go
cells:
  - state: Update/Surge
    event: spec.revision
    windows: [boundary]
    outcome: transition
    to: Update/Surge
    note: retarget the in-flight surge to the new hash; never open a second surge
    invariants: [surge.le.budget, one.operation.per.instance]
    coverage: {perm: [p1234], unit: [TestSurgeRetargetAtBoundary], kind: []}
    status: review
  - state: Update/Surge
    event: timer.retryAt
    windows: [before]
    outcome: n/a
    reason: RetryBlock timers only fire for Instances in Failed
    status: current
```

Field semantics, with the reason each exists:

- **`outcome`** is closed so a script can check exhaustiveness. `transition`
  (go to `to`), `ignore` (observe, no state change), `defer` (no action now;
  requeue and re-evaluate — e.g. a gate denial), `reject` (the event is refused at
  admission or by the controller with a condition), `escalate` (leave the normal
  path: `Failed`, a `RetryBlock`, a relocation directive), `n/a` (the event cannot
  occur in this state; must carry a `reason`), `DECIDE` (nobody has chosen yet).
- **`windows`** lists any of `before`, `boundary`, `after`; omitted (or empty)
  means every window. Part 3 explains why three.
- **`status`** is `current` (the code does this today; my reading, unverified),
  `review` (the bugfix history touched this cell; an owner must confirm), or
  `decided` (an owner confirmed or changed it). Only `decided` cells generate
  cases. Keeping `current` visibly separate from `decided` is the point: the
  table records what we *chose*, not merely what the code happened to do.
- **`decided_in`** names the file that owns the transition. The well-formedness
  test checks the path exists, so a refactor that moves the decision breaks the
  build until the table follows it. That is the anti-rot mechanism.
- **`placement`** is where the cell can be checked: `unit` (a pure decision
  point), `perm` (the real-cluster runner can aim at it), `kind` (needs real
  kubelet timing the runner cannot place), or `sim` (only a deterministic
  simulator can place it; untested until one exists). It is required on every
  `decided` cell that is not `n/a`, so an unplaceable cell is a visible gap
  rather than a silent one.
- **`coverage`** lists the perm case ids, unit test names, and KIND spec files
  that assert this cell. The coverage report (Part 4) joins on it.
- **`history`** is not a field on the cell — bugfix provenance (PR numbers)
  must not live in the neutral table. It lives in a sidecar under
  `hack/omenative-testing/statemachine/history/`, matched to cells by the same
  selector rule (`variants`/`windows`/`transition`) that expansion uses. It is
  what turns `review` from a feeling into a list.

**Authoring form vs the logical grid.** The cell table above is the *logical*
grid. Authors write a compact form that the loader expands to it: a machine is a
directory of fragments (`machine.yaml`, `states.yaml`, `events.yaml`,
`transitions.yaml`, and any number of `cells-*.yaml`) so extraction and review
can proceed one operation family at a time; a state may declare `not_applicable`
per event, which synthesizes the `n/a` cell with its reason for every window and
variant of that event; an event may declare `variants` (e.g. `source`/`target`
pods, the eight waiting reasons, the seven hold gates), each of which is its own
column; and a cell may omit `variants`, `windows`, or `transition` to cover all
of them, or name a `transition` when a state has several outgoing edges and the
boundary or after behavior differs per edge. Expansion is exhaustive by
construction: every (state, event, variant, window, transition) key must resolve
to exactly one authored or synthesized cell, and the build fails otherwise.

### Part 3: the exhaustiveness rule

Enumerating events per state is not enough, because the bugs sit at
transitions. For every transition from S1 to S2 with guard G, each event gets
three cells:

1. **before** — the event arrives in S1 while G is false.
2. **boundary** — the event arrives after G became true but before the
   controller's write for the transition landed. This is the race window:
   promote-before-PodReady, the Sequential zero-time overlap, the
   Expectations observer/dispatcher mismatch, the stale-cache `AlreadyExists` on
   a retried create all live here.
3. **after** — the event arrives in S2, immediately.

"Exhaustive" then has a mechanical meaning. Let A(S) be the events applicable in
state S (the machine declares applicability per state; an event outside A(S)
still gets a cell, with outcome `n/a` and a reason). The table is well-formed when
every (S, E ∈ events, W ∈ windows) triple has exactly one cell. Raw size for the
instance machine is about 20 states × 40 events × 3 windows ≈ 2,400 cells. Most
are `n/a` — `timer.retryAt` is meaningful only in `Failed`; `pod.ready(target)`
only where a target pod exists — and my estimate, to be corrected by the first
extraction, is 400–600 cells with non-trivial outcomes for the instance machine
and a similar number across the other four together.

Why write the `n/a` cells at all? Because an omitted cell and a forgotten cell
look the same. Writing `n/a` with a reason converts "we never thought about it"
into "we decided it cannot happen", which is a claim the extraction can be wrong
about and a reviewer can challenge.

### Part 4: what derives from the tables

Tests become projections of the table. Four projections, in order of how much
each can place:

1. **Perm corpus (real cluster, CPU only).** The runner already polls each IR's
   `instanceStatuses` every tick for invariant A (`run.py:734-783`, `:1960`).
   Firing a verb when an Instance enters `operation.{type,step}` is therefore an
   extension of an existing poll, not a new observer. `during=` grows from
   `{settling, rotating, migrating}` to `<machine>/<state>[@boundary]`, where
   `@boundary` fires on the guard's observable — e.g. the moment the target pod
   reports Ready while the IR still shows step `Surge`. The verb set grows from
   `podkill`, `ctrlrestart`, `cordon` to the operator family: rebump, strategy
   switch, scale up/down, `pause=true|freeze`, unpause, promote, rollback,
   migrate request, annotation-only edit. Cell outcomes map onto the existing
   `expect=` vocabulary — `{reject, roll, noroll, recover, fail}`
   (`run.py:1488`) — plus two new values, `escalate` and `defer`. The generator
   reads the tables and emits one case per `decided` cell that is placeable on a
   real cluster, with a `cell=` header so verdict rows carry the cell id back.
   The per-PR lane cap (`run_test.py`, `test_corpus_stays_under_lane_cap`) stays;
   the tag lets the batch rotate a subset per PR and run everything nightly.
2. **Unit tables at the pure decision points.** The engines expose two pure
   functions: `workload.Plan` performs zero mutations by contract
   (`plan_decision.go:201`) and `coordination.ComputeTransition` reads only its
   observation (`state.go:150`). The canary executor and `rolloutrun.Reconcile`
   are not pure — both read through a client and the canary executor mutates
   status inline — but their decisions are table-testable against a fake client,
   which is how their existing tests already work. Cells decided in those
   functions become table tests whose names carry the cell id. A Go loader parses the same YAML;
   a well-formedness test fails the build if any applicable cell is missing, a
   `decided_in` path does not exist, or a machine marked frozen still has a
   `DECIDE`. A `current` cell whose generated test fails is either a wrong
   extraction or a real bug — both are findings, and the table records which.
3. **KIND specs.** Boundary cells that need real kubelet timing and that the perm
   runner cannot place reliably — UID rotation races, PodGroup-before-pods,
   grace-period termination that never completes — become KIND specs tagged with
   the cell id. The existing watch-driven observer in `omenative_perm_kind`
   enforces the invariants the cell names.
4. **Coverage report.** One script joins cells with perm verdicts (by `cell=`),
   unit test names (from `go test -json`), and KIND tags, and prints per machine:
   decided vs undecided, covered vs uncovered, and the history-touched cells that
   still lack coverage. That is the number to watch instead of the YAML count.

The simulator, later, is projection five: the tables are its scenario generator
(walk states, inject each applicable event in each window) and its oracle
(expected outcome plus named invariants). Nothing in the format changes for it.

### Part 5: process — extract, render, decide, freeze

Order: instance machine first (most states, most history), then coordination
group, canary, rollout run, and component revision last (it is mostly
aggregation). Per machine:

1. **Extract.** From the code, not from the OEPs (Failure mode 4). Fill states,
   events, transitions, and `decided_in`; write every cell as `current`, `n/a`,
   or `review`; pre-annotate each `review` cell with the PRs that motivated it
   and the candidate outcomes. The five extractions are independent and can run
   in parallel.
2. **Render.** A Mermaid state diagram and a state × event heatmap per machine,
   regenerated from the YAML so the picture cannot drift from the table.
3. **Decide.** The owner walks the `review` and `DECIDE` cells, and any `current`
   cell they disagree with. This is where behavior is *chosen* rather than
   inherited. Budget: a few hours per machine, front-loaded on `review` cells.
4. **Freeze and derive.** The well-formedness test turns on for that machine; the
   generator emits its cases; the pure-cell unit tables are written; uncovered
   `decided` cells are listed in the coverage report until they are not.

### Risks and mitigations

- **Extraction is wrong.** My reading of 30K lines will mislabel some `current`
  cells. *Mitigation:* the unit-table projection checks `current` cells against
  the code mechanically; disagreements surface as failing tests before anyone
  relies on the cell. Mitigation, not full fix: cells decided in impure code
  (the op executors) are checked only through the perm runner or KIND.
- **Review load.** Roughly a thousand `decided` cells across five machines is real
  work. *Mitigation:* `review` cells first; `n/a` cells are batch-confirmable per
  row; the heatmap makes a whole row reviewable at a glance.
- **The table rots.** A refactor moves a decision and nobody updates the table.
  *Mitigation:* `decided_in` existence check in the build; a process rule
  (Graduation, stable) that a bugfix PR in these trees cites the cell it changes.
- **Boundary placement on a real cluster is best-effort.** The runner sees the
  guard's observable with latency, so some boundary cells cannot be aimed at
  reliably. *Mitigation:* such cells carry `placement: kind` or
  `placement: sim` explicitly instead of a case that pretends. The count of
  `placement: sim` cells is also the honest sizing input for the simulator OEP.

## Design Details

### The instance machine as extracted (commit `654cde4f`; to be verified in step 1)

States are `phase / operation type / step`, taken from `types.go:43-51`,
`types.go:107-132`, `ops/update_status.go:19-38`, `ops/create.go:28`, and the
literal step strings in `ops/restart.go:419`, `ops/migrate.go:1281`,
`ops/delete_batch.go:264`.

- No operation: `Empty`, `Pending`, `Ready`, `Failed`, `Deleting` (pods gone,
  awaiting GC).
- `Create`: `CreatePods`.
- `Update`: `Surge`, `GangSurgeTarget` (the replacement gang), `SurgeDrain`,
  `SurgeDrainSettle`, `Drain`, `InPlace`, `GangSurgeTargetCleanup`, and the
  recreate wait that follows `Drain` on the `RecreatePod` path.
- `Restart`: `Drain`, then `CreatePods` once the recreate commits
  (`ops/restart.go:158`).
- `Migrate`: `CreateSurge`, then the surge-ready drain of the source.
- `Delete`: `Drain`.

Kept as guards, not states, so the state id stays reviewable: the
`minReadySeconds` window, the `RetryBlock` state for the target revision
(`Backoff`, `RetryInProgress`, `Held`), the incarnation, and single-pod vs gang.
Any cell may reference them in its guard; they do not multiply the rows.

Event families, about 40 events in total:

- **pod** (from the kubelet and scheduler): scheduled, `ContainersReady`, Ready,
  serving gate on/off, waiting with reason ∈ {`ImagePullBackOff`, `ErrImagePull`,
  `InvalidImageName`, `CreateContainerConfigError`, `CreateContainerError`,
  `CrashLoopBackOff`, `RunContainerError`, `DeadlineExceeded`} — the set the
  disposition code classifies (`disposition.go:65-70` and the escalation paths),
  container restart, deleted, UID rotated, stuck `Terminating`, node lost,
  scheduling-gated, evicted.
- **operator** (spec and annotations): revision bump (new hash), annotation-only
  edit (must *not* roll; the revision-hash exclusion series), strategy switch,
  replicas up, replicas down, `pause=true`, `pause=freeze`, unpause, teardown,
  migrate request, partition change.
- **coordination**: `gate.allow`, `gate.deny(gate)` for the seven hold gates.
- **timer**: step deadline, `minReadySeconds`, `RetryBlock.nextRetryAt`,
  Expectations TTL, `progressDeadlineSeconds`, drain settle.
- **controller**: crash (in-memory Expectations and caches lost), stale cache
  read (the `Client` vs `APIReader` split in `workload/types/deps.go:13-21` is
  exactly where this event enters).
- **apiserver**: conflict (409), `AlreadyExists`, `NotFound`, quota denied.

### Deciding functions, per machine

These are the `decided_in` anchors the extraction starts from. They are also the
seams the unit-table projection tests against.

| Machine | Decision entry | Purity today |
|---|---|---|
| Instance | `workload.Plan` (`plan_decision.go:201`) for action selection; `ops/*.go` executors for step advancement | `Plan` pure by contract; executors write mid-operation |
| Component | `irprojector` (IR spec projection) and IR status aggregation (`inferencereplica/status.go`) | aggregation pure; projection writes |
| Group | `coordination.ComputeTransition` (`state.go:150`); gates via `EvaluateUpdateGate` (`gate_eval.go:56`), called from `inferencereplica/convert.go:212` | `ComputeTransition` pure; gates read-only |
| Canary | `canary.Reconcile` (`canary/reconciler.go:131`) | mutates status inline; inputs are values |
| Run | `rolloutrun.Reconcile` (`rolloutrun.go:93`) | reads via `Reader`; outcome is a value |

Where a transition is decided in impure code, the table still names the file; the
projection for that cell is the perm runner or KIND rather than a unit table, and
the cell says so via `placement`.

### Runner changes (`hack/omenative-testing/perm`)

All additive; the default `mode=rollout` path is untouched, as `run.py:1403-1404`
requires.

- `during=<machine>/<state>[@boundary]` alongside the existing values. Detection
  for instance states uses the per-tick IR poll that invariant A already performs;
  `@boundary` additionally watches the pod stream for the guard's observable
  named in the cell.
- Verb hook: today's `fault=` kinds plus `verb=` for the operator family listed
  above. Each verb is a `kubectl patch` or annotation the runner already knows
  how to issue in some mode (`rebump`, `scaledown`, `pause=`, `promote`, the
  migration annotation); the change is letting any of them fire at a `during=`
  hook.
- `expect=` gains `escalate` (the Instance ends `Failed` with the named
  `RetryBlock`/directive) and `defer` (no action until the named condition, then
  the `to` state).
- `cell=<machine>/<state>/<event>/<window>` header, echoed into the verdict TSV.
- `--validate-only` learns the new keys, so a malformed generated header fails
  with zero cluster access, as today.

### Go loader and well-formedness test

Location: `tests/rolloutspec/` (tables under `machines/`, `loader.go`,
`wellformed_test.go`). It lives under `tests/` because the tables are spec
data with a loader and a build gate, not controller code: `wellformed_test.go`
asserts grid completeness, not runtime behavior, and nothing here ships in the
binary. TODO: confirm the PR-number `history` field is acceptable under the
neutrality rules or move it to a sidecar file kept under `hack/`.

The test asserts: every state id and event id referenced by a cell is declared;
every (state, event, window) triple has exactly one cell; every `n/a` has a
reason; every `decided_in` path exists; a machine with `frozen: true` has no
`DECIDE`. It does not assert anything about controller behavior.

### Rendering and coverage

`hack/omenative-testing/statemachine/render.py` emits, per machine, a Mermaid
`stateDiagram-v2` from `transitions` and a heatmap (states × events, one panel
per window) colored by outcome and hatched by status. `coverage.py` performs the
join in Part 4 and prints the per-machine table. Both are internal tooling and
stay under `hack/`.

The review artifacts sit beside that tooling for the same reason: the per-family
tables, the roll-up (`review/REVIEW-instance.md`), the open-PR cross-check and
the event audits live under `hack/omenative-testing/statemachine/`, because they
cite PR numbers and the OEP tree keeps those out. The implementation history —
the plans each extraction step was executed from — is in this branch's commit
log rather than in the OEP directory.

## Test Plan

This OEP is test infrastructure; its own tests check the artifact, not the
controllers.

- `wellformed_test.go` in CI from the first machine onward.
- A round-trip test per frozen machine: every `decided` cell with a unit
  placement has a test whose name carries the cell id, and the test passes.
- `generate_cases.py --check` byte-stability extends to the cell-derived cases.
- `run.py --validate-only` accepts the new header keys and rejects unknown cell
  ids.
- Manual, once per machine: the rendered heatmap is reviewed against the table
  by a second reader.

## Graduation Criteria

### Alpha

- Instance machine frozen; well-formedness test in CI.
- Runner supports `during=<state>` for instance states and the `cell=` tag.
- Coverage report runs; every `history`-touched instance cell has at least one
  placement.

### Beta

- All five machines frozen.
- Coverage report in CI as a soft gate; history-touched cells across all machines
  100% covered.
- At least one fix has shipped as "cell X changed from `current` to `decided`",
  proving the table drives the code rather than describing it.

### Stable

- Process rule in force: a `[Bugfix]` PR touching either engine tree cites the
  cell(s) it changes, and the table change is in the same PR.
- The simulator OEP consumes the tables unchanged.

## Drawbacks

- **It is a lot of cells.** About a thousand decided cells is the price of the
  word "exhaustive". The alternative — deciding cells one incident at a time — has
  cost 67 bugfix commits in the last 120.
- **A table can lie.** A `decided` cell nobody tests is a promise, not a fact.
  The coverage report exists to keep that list visible, and the round-trip test
  keeps the unit-placed cells honest.
- **Real-cluster placement is approximate.** Some boundary cells will be marked
  `placement: sim` and stay untested until the simulator exists. That is a true
  gap, stated rather than hidden.

## Alternatives

1. **Build the deterministic simulator first.** A seeded, in-process run of the
   real reconcilers against a fake apiserver and a kubelet model would explore
   interleavings automatically. *Tradeoff:* it needs an oracle, and without the
   tables the oracle is a handful of invariants plus "it converged", which finds
   crashes and hangs but not "it did the wrong legal thing". The tables *are* the
   oracle. I recommend sequencing the simulator after the instance machine is
   frozen, as its own OEP.
2. **A formal spec (TLA+ or P) with model checking.** *Tradeoff:* a second
   language nobody on the team reviews daily, and the conformance gap between
   model and Go is the hard part. The tables are precise enough to generate a
   model from later; today the projections give us executable checking without
   the translation.
3. **Refactor the engines into explicit transition tables in Go first.**
   *Tradeoff:* the op executors are impure by nature (they write mid-operation),
   the two trees took 213 commits between 2026-06-01 and 2026-09-14, and the
   dominant bugs are timing interleavings that a table refactor does not address. Seam refactors should be
   demand-driven by cells that turn out to be untestable.
4. **Keep growing the perm corpus along its configuration axes.** *Tradeoff:*
   940 cases already; the axis that is missing is timing, and configuration
   permutations do not add it.
5. **Author the tables in Go rather than YAML.** *Tradeoff:* the compiler checks
   ids for free, but the Python generator cannot consume Go, and the heatmap
   renderer would need a Go emitter. The loader's id validation recovers most of
   the compiler's benefit. YAML, with the loader as the type checker.

## Open Questions

- **Boundary placement fidelity.** Which boundary cells can the real-cluster

  `placement: sim`? Unknown until the first extraction; the answer sizes the
  simulator OEP. Owner: TBD.
- **Composed scenarios.** Chaining cells across machines is unbounded. Start with
  pairs the bugfix history touched (e.g. group `Waiting` × instance
  `SurgeDrain`), and decide after the instance machine is frozen whether to
  generate more. Owner: TBD.

- **Annotation-only edits.** Their own event (`spec.annotation`) or a guard on
